1. Use Case Diagram Blueprint

A systematic, step-by-step system for drawing a full-marks UML Use Case Diagram (Wits INFO2001A Systems Analysis). It is the high-level picture of the system boundary, the external users (actors) and the services or goals the system provides (use cases). It says what the system does, never how.

What the diagram contains

Four building blocks, each with one fixed way of being drawn:

ElementHow it is drawnRule
System boundaryOne outer rectangle with the system name in its headerUse cases go inside
ActorStick figure (external systems too, labelled as such)Always outside the rectangle
Use caseOval holding a Verb-Noun labelActive verb: Create Request, not Form
AssociationSolid line from an actor to a use caseNo arrow-heads on actor lines

The 6-Step Universal Use Case Blueprint

Steps 1 to 3 place the elements, Step 4 connects them, Step 5 adds the stereotypes and Step 6 audits the result. Worked examples use #TutAcadSupport and the Wits Gym booking system.

Read the diagram left to right: the order of the cards is the order you work in.

Step 1: Draw the System Boundary

Draw one rectangle and put the system name in its header, e.g. System Boundary: #TutAcadSupport Management System. Everything the system is responsible for goes inside; everything else stays outside.

Step 2: Identify the External Actors

An actor is anyone (or any other system) that interacts with the system from outside it. Draw each as a stick figure beside the boundary: primary actors on the left, supporting actors on the right.

SystemActorsType
#TutAcadSupportStudent, Tutor, AdministratorAll human actors
Wits Gym BookingGymMember, GymClerkPrimary actors
Wits Gym BookingPersonalTrainerSecondary actor
Wits Gym BookingPaymentGatewayExternal system actor

Step 3: Identify the Use Cases (Verb-Noun Ovals)

Each oval is one goal the system delivers. Start every label with an active verb.

SystemUse cases
#TutAcadSupportCreate Tutoring Request, Verify Student Eligibility, Escalate Aged Request, Conduct Tutoring Session, Approve Tutor Application
Wits Gym BookingSearch Member Record, Register New Member, Book Training Session, Process Session Payment, Update Trainer Availability

Step 4: Connect the Associations

Join each actor to the use cases it takes part in with a solid line.

SystemAssociations
#TutAcadSupportStudent to Create Tutoring Request
Tutor to Conduct Tutoring Session
Administrator to Approve Tutor Application
Wits Gym BookingGymClerk to Search Member Record
GymClerk to Book Training Session
PersonalTrainer to Update Trainer Availability
Book Training Session to PaymentGateway

Step 5: Add the Stereotypes (<<includes>> and <<extends>>)

Both are dashed arrows labelled with the stereotype in guillemets. They differ in when the second use case runs and in which way the arrow points.

StereotypeMeaningArrow directionTrigger words
<<includes>>The sub-task is mandatory: the base use case never finishes without itBase use case to the included sub-task"always", "must first", "is required"
<<extends>>The extension is conditional: it runs only when a condition is metExtension use case to the base use case"only if", "when", "if not found"

Worked example 1: #TutAcadSupport Management System

StereotypeFrom and toWhy
<<includes>>Create Tutoring Request to Verify Student EligibilityVerification is a mandatory step
<<extends>>Escalate Aged Request to Create Tutoring RequestRuns only if the request has been pending for more than 7 days

Actors sit outside the boundary. Solid lines join an actor to a use case; dashed arrows carry the stereotype.

Worked example 2: Wits Gym Personal Training Booking System

StereotypeFrom and toWhy
<<includes>>Book Training Session to Process Session PaymentPayment is mandatory for a booking
<<extends>>Register New Member to Search Member RecordTriggered only if the member record is not found during the search

PaymentGateway is an external system actor: it sits outside the boundary like any human actor.

Note: GymMember is listed as a primary actor but has no associations in this scenario, so it is left off the picture. An actor with no use case would normally be given one or removed.

Step 6: Audit & Scope Check

Verify the finished diagram against these gates before you submit it.

CriterionRequirementCheck
Actors outsideAll stick figures are placed strictly outside the rectangle☐
Verb-Noun ovalsEvery use case uses an active verb (Create Request, not Form)☐
<<includes>> directionArrow runs from the base use case to the included sub-task☐
<<extends>> directionArrow runs from the extension use case to the base use case☐
Mandatory vs conditionalincludes is used only for mandatory steps; extends only for conditional ones☐
ScopeEvery oval is inside the boundary and every actor line ends on an oval☐
Exam workflow: draw the boundary (Step 1), place the actors outside it (Step 2), list the Verb-Noun ovals (Step 3), join them with solid lines (Step 4), mark mandatory and conditional steps with the two stereotypes (Step 5), then tick the audit table (Step 6).

2. Domain Model Class Diagram Blueprint

A systematic, step-by-step system for drawing a full-marks Domain Model Class Diagram (Wits INFO2001A Systems Analysis). It shows the real-world concepts, entities, attributes and business rules of the problem domain, in the client's language rather than the programmer's.

Analysis vs design

Do not confuse the two class diagrams. This blueprint is the analysis one.

DiagramModelsWhat the boxes contain
Domain Model Class Diagram (analysis)The client's real-world business domainAttributes only: no visibility modifiers (-, +), no data types, no methods, no primary or foreign keys
Design Class Diagram (design)The software implementationMethods, visibility markers, parameters and programming types

The 6-Step Domain Class Diagram Blueprint

Steps 1 and 2 find the classes and their attributes, Steps 3 and 4 link them, Step 5 handles the advanced structures and Step 6 audits the result. Worked examples use #TutAcadSupport and the Wits Room Rental system.

Read the diagram left to right: the order of the cards is the order you work in.

Step 1: Identify the Domain Classes (Nouns)

Underline every noun in the scenario that has its own details worth recording. Write each as ALL_CAPS_SINGULAR: STUDENT, never Students.

SystemScenarioExtracted classes
#TutAcadSupportStudents submit tutoring requests for specific courses. Tutors are assigned to conduct tutoring sessions. Students and tutors are both people with personal details.PERSON (superclass), STUDENT, TUTOR, TUTORING_REQUEST, TUTOR_SESSION, COURSE
Wits Room RentalProperty owners register rental rooms. Students (tenants) sign lease agreements to rent rooms. Monthly rent payments are tracked for each lease.PROPERTY_OWNER, RENTAL_ROOM, TENANT, LEASE_AGREEMENT (association class resolving M:N), RENT_PAYMENT

Step 2: Define the Attributes

Write attributes in lower_case and start each with its class prefix (student_degree). No PK or FK tags, no data types, no methods.

ClassAttributes
PERSONperson_id, person_fname, person_lname, person_email
STUDENTstudent_degree, student_year_level
TUTORtutor_rating, tutor_hourly_rate
TUTORING_REQUESTrequest_id, request_date, request_status, request_urgency
TUTOR_SESSIONsession_date, session_duration, session_venue
COURSEcourse_code, course_name
PROPERTY_OWNERowner_id, owner_fname, owner_phone
RENTAL_ROOMroom_number, room_type, monthly_rate
TENANTtenant_id, tenant_fname, tenant_student_no
LEASE_AGREEMENTlease_start_date, lease_end_date, deposit_amount
RENT_PAYMENTpayment_reference, payment_date, amount_paid

Step 3: Establish the Associations & Business Rules

Turn each verb in the scenario into a named association, written as verb -> so the reader knows which way to read it.

SystemRuleAssociation
#TutAcadSupportA STUDENT submits a TUTORING_REQUESTsubmits ->
#TutAcadSupportA TUTOR conducts a TUTOR_SESSIONconducts ->
#TutAcadSupportA TUTORING_REQUEST pertains to a COURSEpertains_to ->
#TutAcadSupportSTUDENT and TUTOR inherit from PERSONGeneralisation hierarchy
Wits Room RentalA PROPERTY_OWNER owns one or more RENTAL_ROOMsowns ->
Wits Room RentalA TENANT rents a RENTAL_ROOM through a LEASE_AGREEMENTrents ->
Wits Room RentalA LEASE_AGREEMENT generates RENT_PAYMENT recordsgenerates ->

Step 4: Define the Multiplicities

Put a multiplicity at both ends of every association. Ask "must there be one?" (WILL) or "might there be none?" (MAY).

MultiplicityReads as
1..1Exactly one (it will exist)
0..1Zero or one (it may exist)
1..*One or many (at least one will exist)
0..*Zero or many (any number may exist)
AssociationMultiplicitiesReasoning
STUDENT submits TUTORING_REQUEST1..1 to 0..*A request belongs to one student, who may submit many requests
TUTORING_REQUEST pertains to COURSE0..* to 1..1Each request names exactly one course
TUTOR conducts TUTOR_SESSION1..1 to 0..*A tutor may conduct zero or many sessions
PROPERTY_OWNER owns RENTAL_ROOM1..1 to 1..*An owner has at least one room
TENANT rents RENTAL_ROOM0..* to 0..*M:N: a tenant may rent many rooms over time and a room may have many tenants over time
LEASE_AGREEMENT generates RENT_PAYMENT1..1 to 0..*A lease generates zero or many payments

Worked example 1: #TutAcadSupport

Class names are ALL_CAPS_SINGULAR; boxes hold attributes only: no types, no visibility marks, no keys, no methods.

Worked example 2: Wits Room Rental & Tenant System

The many-to-many link between TENANT and RENTAL_ROOM is resolved by the association class LEASE_AGREEMENT, tied to the association by a dashed line.

Verify the finished diagram against these exam gates.

Exam workflow: underline the nouns (Step 1), list their attributes (Step 2), turn the verbs into arrows (Step 3), add multiplicities (Step 4), mark inheritance, composition and association classes (Step 5), then tick the audit table (Step 6).

3. Entity Relationship Diagram (ERD) Blueprint

A systematic, step-by-step system for turning a domain class diagram into a full-marks Entity Relationship Diagram (Wits INFO2001A Database Design). The ERD is the relational schema, ready to implement in an RDBMS such as Microsoft Access.

What an ERD aligns with

The ERD is the design-level step that follows the analysis class diagram, so it must agree with it entity for entity.

ArtifactWhat the ERD takes from it
Domain Model Class DiagramThe classes (become tables), attributes (become columns), associations and multiplicities
Data DictionaryThe data type, size and constraint of every column, checked in the final audit

The 6-Step Universal ERD Blueprint

Steps 1 to 3 reshape the class diagram into tables, Steps 4 and 5 set the relationships and keys, Step 6 audits the schema. Worked examples use #TutAcadSupport and the Wits Gym booking system.

Read the diagram left to right: the order of the cards is the order you work in.

Step 1: Domain Alignment & Entity Mapping

Take the input class diagram and make every class an entity named ALL_CAPS_SINGULAR. Remove every method (submitRequest(), verifyEligibility()): a table holds data, not behaviour.

SystemEntities
#TutAcadSupportSTUDENT, TUTOR, TUTORING_REQUEST, TUTOR_SESSION, COURSE
Wits Gym BookingMEMBER, TRAINER, TRAINING_SESSION, BOOKING

Step 2: Translate Hierarchies & Whole-Part Relationships

A relational table has no inheritance or composition, so translate each one.

StructureTranslationExample
Inheritance, strategy 2 (separate tables)One table per class. Each subclass takes its PK as an FK to the superclass tablePERSON (PersonNo PK); STUDENT (StudentNo PK FK pointing to PERSON.PersonNo); TUTOR (TutorNo PK FK pointing to PERSON.PersonNo)
CompositionBecomes an ordinary 1:M relationshipTRAINER possesses TRAINER_AVAILABILITY slots

Step 3: Resolve the Many-to-Many (M:N) Relationships

An ERD may never contain an M:N line. Replace each one with a bridge entity (junction table) that holds one FK to each side, plus its own PK.

SystemM:N connectionBridge entity and keys
#TutAcadSupportSTUDENT (0..*) submits requests for COURSE (0..*)TUTORING_REQUEST: RequestID PK, StudentNo FK1, CourseCode FK2
Wits Gym BookingMEMBER (0..*) books sessions with TRAINER (0..*)BOOKING: BookingID PK, MemberNo FK1, TrainerID FK2

Step 4: Define the Multiplicities & Participation

Label both ends of every relationship line. The bridge entity always ends up on the 0..* side of both parents.

SystemRelationshipMultiplicity
#TutAcadSupportSTUDENT to TUTORING_REQUEST1..1 to 0..*
#TutAcadSupportCOURSE to TUTORING_REQUEST1..1 to 0..*
#TutAcadSupportTUTOR to TUTOR_SESSION1..1 to 0..*
Wits Gym BookingMEMBER to BOOKING1..1 to 0..*
Wits Gym BookingTRAINER to BOOKING1..1 to 0..*
Wits Gym BookingBOOKING to PAYMENT_RECEIPT1..1 to 0..1

Step 5: Assign Primary Keys (PK) & Foreign Keys (FK)

Give every table a PK. Put each FK on the M-side of its 1:M relationship. Number the FKs (FK1, FK2) when a table has more than one.

TableColumns with keys
STUDENTStudentNo PK
COURSECourseCode PK
TUTORING_REQUESTRequestID PK, StudentNo FK1, CourseCode FK2
TUTOR_SESSIONSessionID PK, RequestID FK1, TutorNo FK2
MEMBERMemberNo PK
TRAINERTrainerID PK
BOOKINGBookingID PK, MemberNo FK1, TrainerID FK2, SessionDate, BookingStatus
PAYMENT_RECEIPTReceiptNo PK, BookingID FK, AmountPaid, PaymentDate

Step 6: Final Diagram & Data Dictionary Audit

Draw the tables with their keys, then check every column against the Data Dictionary for type and key.

Worked example 1: #TutAcadSupport relational schema

TUTORING_REQUEST is the bridge entity between STUDENT and COURSE. Every foreign key sits on the M-side (the 0..* end).

Worked example 2: Wits Gym Booking relational schema

BOOKING resolves the many-to-many link between MEMBER and TRAINER. A TRAINER_AVAILABILITY table would hang off TRAINER as a plain 1:M relationship.

Note on the first diagram: the 1..1 and 0..1 labels on the PERSON links show that every student or tutor row is exactly one person, while a person need not be either.

Quality Audit Checklist for Exams

CriterionRequirementCheck
Capital singular namesTables are ALL_CAPS_SINGULAR (STUDENT, BOOKING)☐
No M:N linesEvery many-to-many relationship is broken by a bridge entity☐
FK placementForeign keys sit on the M-side of every 1:M relationship☐
Keys completeEvery table has a PK; every FK is tagged FK (numbered when there are several)☐

Exam workflow: convert each class to a table (Step 1), translate inheritance and composition (Step 2), replace M:N lines with bridge tables (Step 3), label both ends (Step 4), add PKs and FKs (Step 5), then audit against the data dictionary (Step 6).

4. Functional Dependency & Normalisation Blueprint

A systematic, step-by-step system for drawing Functional Dependency Diagrams and normalising a table through its states UNF, 1NF, 2NF and 3NF (Wits INFO2001A Database Normalisation). The diagram shows which attributes determine which, so you can spot the dependencies that break a normal form.

What a functional dependency is

A functional dependency X -> Y means the value of X (the determinant) uniquely determines the value of Y (the dependent).

TypePatternEffect
Full functional dependency(PK_Part1, PK_Part2) -> NonKey_AttributeAllowed in 2NF and 3NF
Partial dependencyPK_Part1 -> NonKey_AttributeViolates 2NF
Transitive dependencyNonKey_Determinant -> NonKey_AttributeViolates 3NF

The Four Normalisation Stages

Work through the states in order. Each stage removes one kind of problem. Worked examples use a tutoring-session table and a property-rental invoice table.

Read the diagram left to right: the order of the cards is the order you work in.

Phase 0: Unnormalised Form (UNF)

Start from the raw record. Multivalued cells are present: one row holds several values in a single cell.

ExampleAttributesWhat is wrong in UNF
1. Student tutoring session{Student_ID, Student_Name, Course_Code, Course_Name, Tutor_ID, Tutor_Name, Session_Date, Session_Rating}A single student row holds several courses, tutors and session dates as comma-separated strings
2. Property rental & lease invoice{Lease_ID, Lease_Start_Date, Tenant_ID, Tenant_Name, Tenant_Phone, Room_ID, Building_Name, Monthly_Rent, Invoice_ID, Invoice_Date, Amount_Due}A raw receipt lists the tenant, the leased room and several monthly invoice rows in one record

Phase 1: Convert to 1NF (Atomic Data & Composite Primary Key)

  1. Flatten the table: expand each multivalued list into its own atomic row.
  2. Identify the composite primary key: the smallest set of attributes that makes every row unique.
  3. Map the 1NF dependencies: draw every full, partial and transitive dependency on the diagram.

Worked example 1: Student tutoring session

Composite PK: (Student_ID, Course_Code, Tutor_ID, Session_Date)

TypeDependency
Full(Student_ID, Course_Code, Tutor_ID, Session_Date) -> Session_Rating
Partial 1Student_ID -> Student_Name (depends on part of the PK)
Partial 2Course_Code -> Course_Name (depends on part of the PK)
Partial 3Tutor_ID -> Tutor_Name (depends on part of the PK)

The underlined orange boxes are the composite primary key. Every partial arrow starts at only part of that key.

Worked example 2: Property rental & lease invoice

Composite PK: (Lease_ID, Invoice_ID). Each row is a single invoice line.

TypeDependency
Full(Lease_ID, Invoice_ID) -> Amount_Due
Partial 1Lease_ID -> Lease_Start_Date, Tenant_ID, Tenant_Name, Tenant_Phone, Room_ID, Building_Name, Monthly_Rent
Partial 2Invoice_ID -> Invoice_Date
Transitive (inside the lease attributes)Tenant_ID -> Tenant_Name, Tenant_Phone

Lease_ID reaches all seven lease attributes. Tenant_ID then determines Tenant_Name and Tenant_Phone, the transitive dependency.

Phase 2: Convert to 2NF (Eliminate Partial Dependencies)

Decompose the table so every non-key attribute depends on the whole of its primary key. Each determinant of a partial dependency becomes the PK of a new table.

Worked example 1: Student tutoring session

TablePrimary keyForeign keysAttributesState
STUDENTStudent_ID-Student_ID, Student_Name3NF
COURSECourse_Code-Course_Code, Course_Name3NF
TUTORTutor_ID-Tutor_ID, Tutor_Name3NF
TUTOR_SESSION(Student_ID, Course_Code, Tutor_ID, Session_Date)Student_ID FK1, Course_Code FK2, Tutor_ID FK3Student_ID, Course_Code, Tutor_ID, Session_Date, Session_Rating3NF

Worked example 2: Property rental & lease invoice

TablePrimary keyAttributesState
INVOICE_LINE(Lease_ID, Invoice_ID)Lease_ID, Invoice_ID, Amount_Due2NF
INVOICEInvoice_IDInvoice_ID, Invoice_Date3NF
LEASE_DETAILSLease_IDLease_ID, Lease_Start_Date, Tenant_ID, Tenant_Name, Tenant_Phone, Room_ID, Building_Name, Monthly_RentViolates 3NF: Tenant_ID -> Tenant_Name, Tenant_Phone

Phase 3: Convert to 3NF (Eliminate Transitive Dependencies)

Check each 2NF table for a non-key attribute that determines another non-key attribute. Extract it into its own table and leave the determinant behind as a foreign key.

Worked example 1: Student tutoring session

Every table from Phase 2 has non-key attributes that depend directly and exclusively on their primary key. No transitive dependencies exist, so the four tables are already in 3NF.

Worked example 2: Property rental & lease invoice

Decompose LEASE_DETAILS: extract TENANT into its own table and keep Tenant_ID in the lease table as an FK.

TablePrimary keyForeign keyAttributesState
INVOICE_LINE(Lease_ID, Invoice_ID)-Lease_ID, Invoice_ID, Amount_Due3NF
INVOICEInvoice_ID-Invoice_ID, Invoice_Date3NF
TENANTTenant_ID-Tenant_ID, Tenant_Name, Tenant_Phone3NF
LEASELease_IDTenant_ID FKLease_ID, Lease_Start_Date, Tenant_ID FK, Room_ID, Building_Name, Monthly_Rent3NF
Extra check: in LEASE, ask whether Room_ID determines Building_Name and Monthly_Rent in your scenario. If it does, that is a second transitive dependency and ROOM must be extracted the same way.

Key Exam Rules

CriterionRequirementCheck
Partial key checkPartial dependencies exist only if the table has a composite primary key☐
FK persistenceWhen you extract a transitive dependency A -> B, the determinant A must remain in the parent table as an FK☐
Atomic cellsNo cell holds a list of values once the table is in 1NF☐
Dependency types labelledEvery arrow on the diagram is marked full, partial or transitive☐
Lossless splitEvery new table keeps the key needed to join it back to its source☐
Exam workflow: flatten the data and choose the composite key (Phase 1), draw every dependency, move each partial dependency into its own table (Phase 2), then move each transitive dependency into its own table while keeping the determinant as an FK (Phase 3).

5. Design Sequence Diagram (DSD) Blueprint

A systematic, step-by-step system for turning any business narrative into a full-marks Design Sequence Diagram (Wits INFO2001A). Strip the narrative into a three-layer architecture, order the messages in time, pick the right object-lifecycle pattern, then wrap the logic in interaction frames.

Phase 1: The "Narrative Demolition" (Extraction)

Before drawing a single line, strip the narrative into the Three-Layer Architecture:

Read the diagram left to right: the order of the cards is the order of the lifelines on your page.

Phase 2: Chronological Flow & Message Orchestration

A sequence diagram is time-ordered. Read the narrative vertically from top to bottom and write the messages left to right across the layers.

The numbers match the steps in the table below: 1 Actor initiates, 2 Boundary delegates, 3 Controller orchestrates, 4 confirmations return.

StepWhat happens
1. Actor initiatesThe Actor triggers an action on the UI with a solid request arrow.
2. Boundary delegatesThe Boundary immediately passes the input data to the Controller with a solid request arrow.
3. Controller orchestratesThe Controller sends requests (method calls) to Entity lifelines to retrieve, update or create data.
4. Confirmations returnAnswers flow backwards as dashed return arrows (or variable assignments) until the Boundary shows the final output to the Actor.

Don't throw marks away on formatting - examiners grade these visual rules strictly. Tick each one off before you hand in.

Phase 5: Nesting Programming Logic (Interaction Frames)

To model structural logic, surround your messages with rectangular interaction frames.

1. The loop frame (repetition)

Use when the narrative says "for each item", "repeats" or "loops until". Draw a rectangle around the repeating messages, put loop in the top-left tab, and write the guard in square brackets, e.g. [for each product to add].

Reads as: repeat both messages once for every item in the cart. The guard sits in square brackets next to the tab.

2. The alt frame (if-then-else)

Use when there are mutually exclusive outcomes, e.g. "if login is valid... if login is invalid...". Draw one large rectangle around both paths with alt in the top-left tab. Crucial step: split the box in two with a dashed horizontal line. The top half gets the guard [isValid = true], the bottom half [isValid = false].

Reads as: the handler checks the credentials and returns isValid before the frame, so the guards have something to test. If valid go to the main menu, otherwise go to the failure screen. The dashed divider separates the two halves, and each half has its own guard.

3. The opt frame (optional processing)

Use when the logic goes one way only, e.g. "if the trainer is available, then save the booking". There is no else block. Enclose only the conditional steps, put opt in the top-left tab and add a guard such as [isAvailable = true].

Reads as: only if the trainer is available, create the booking. There is no else half. Note the created Booking box drops down to its own step.

4. The ref frame (invoking another diagram)

Use when the scenario hands off to another complete use case, e.g. "the customer's details are retrieved using another sequence diagram". Draw a clean box spanning the lifelines involved, put ref in the top-left tab and write the name of the referenced use case inside.

Reads as: at this point run the whole Validate Customer diagram, then carry on. Nothing is drawn inside the box except the name; it spans the lifelines it touches.

FrameTrigger wordsGuardRemember

Linking the Wireframe to C# & ADO.NET

The click handler below shows how the wireframe's controls reach the database through the three-layer architecture: validate on the Boundary, then delegate to the Controller.

// Event handler for the primary action button [Submit Request]
private void btnSubmitRequest_Click(object sender, EventArgs e)
{
    // 1. Clear previous ErrorProvider messages
    errorProvider1.Clear();
    bool isValid = true;

    // 2. Client-side validation (error prevention)
    if (cboCourse.SelectedIndex == -1)
    {
        errorProvider1.SetError(cboCourse, "Please select a valid course.");
        isValid = false;
    }
    if (cboSupportType.SelectedIndex == -1)
    {
        errorProvider1.SetError(cboSupportType, "Please select a support type.");
        isValid = false;
    }
    if (dtpPreferredDate.Value.Date <= DateTime.Today)
    {
        errorProvider1.SetError(dtpPreferredDate, "Preferred date must be in the future.");
        isValid = false;
    }
    if (string.IsNullOrWhiteSpace(txtDescription.Text))
    {
        errorProvider1.SetError(txtDescription, "Please provide a brief description.");
        isValid = false;
    }
    if (!isValid) return;               // block execution, never reach the controller

    // 3. Prevent duplicate submissions (Nielsen #1: system status)
    btnSubmitRequest.Enabled = false;
    lblMessage.Text = "Processing request submission...";

    try
    {
        // ValueMember gives the FK value, not the displayed text
        string courseCode = cboCourse.SelectedValue.ToString();
        string supportType = cboSupportType.SelectedItem.ToString();
        string priority = radHigh.Checked ? "High" : (radLow.Checked ? "Low" : "Medium");

        // 4. Delegate to the controller (three-layer architecture)
        bool success = requestHandler.createTutoringRequest(
            Session.CurrentStudent.StudentNo,
            courseCode, supportType, priority,
            dtpPreferredDate.Value, txtDescription.Text.Trim());

        if (success)
        {
            MessageBox.Show("Tutoring request successfully submitted!", "Success",
                            MessageBoxButtons.OK, MessageBoxIcon.Information);
            this.Close();               // return to the launcher
        }
    }
    catch (Exception ex)
    {
        MessageBox.Show("Database error: " + ex.Message, "System Error",
                        MessageBoxButtons.OK, MessageBoxIcon.Error);
    }
    finally
    {
        btnSubmitRequest.Enabled = true;
        lblMessage.Text = "Ready";
    }
}

8. Report Blueprint

A systematic, step-by-step system for creating and drawing a full-marks decision-oriented report (Wits INFO2001A). A report is not a data dump: listing every column of a table is invalid design. A report earns its place only by helping a specific recipient make a defensible, timely business decision.

Report vs the other blueprints

The DSD, wireframe and storyboard design how data goes in. A report designs how it comes out. Design always flows backwards from the decision:

Design starts at the decision (card 1) and ends at the format and prototype (card 6).

ArtifactWhat the report takes from it
ERD & Data DictionaryEvery displayed column must trace to an entity attribute, or be defined as a derived calculation with an explicit formula
SQL (Sections 1 to 14)The report is the result of a query: SELECT, INNER JOIN, WHERE, GROUP BY, HAVING, ORDER BY
Interaction & UX principlesNielsen's heuristics for a clean layout: no decorative clutter, clear headers, aligned columns

3. ERD mapping & SQL retrieval

ItemDetail
Source tablesTUTORINGREQUEST (tr), STUDENT (s), COURSE (c)
Derived fieldDays Pending = Date() - tr.SubmissionDate
SELECT 
    tr.RequestID,
    s.StudentNo,
    s.StudentFName & ' ' & s.StudentLName AS StudentName,
    c.CourseCode,
    tr.PriorityLevel,
    tr.SubmissionDate,
    DateDiff('d', tr.SubmissionDate, Date()) AS DaysPending
FROM (TUTORINGREQUEST tr
INNER JOIN STUDENT s ON tr.StudentNo = s.StudentNo)
INNER JOIN COURSE c ON tr.CourseCode = c.CourseCode
WHERE tr.Status = 'Submitted' 
  AND DateDiff('d', tr.SubmissionDate, Date()) >= 7
ORDER BY DateDiff('d', tr.SubmissionDate, Date()) DESC;

ItemDetail
Source tablesTUTOR (t), TUTORINGSESSION (ts), COURSE (c)
Derived fieldCompletion Rate = (COUNT(Completed) / COUNT(Total)) * 100
SELECT 
    t.TutorID,
    t.TutorFName & ' ' & t.TutorLName AS TutorName,
    c.CourseCode,
    COUNT(ts.SessionID) AS ScheduledSessions,
    SUM(IIF(ts.Status = 'Completed', 1, 0)) AS CompletedSessions,
    FORMAT((SUM(IIF(ts.Status = 'Completed', 1, 0)) / COUNT(ts.SessionID)) * 100, "0.0") & '%' AS CompletionRate
FROM (TUTOR t
INNER JOIN TUTORINGSESSION ts ON t.TutorID = ts.TutorID)
INNER JOIN COURSE c ON ts.CourseCode = c.CourseCode
WHERE ts.SessionDate BETWEEN #10/01/2026# AND #10/31/2026#
GROUP BY t.TutorID, t.TutorFName, t.TutorLName, c.CourseCode
ORDER BY COUNT(ts.SessionID) DESC;
