1. Basic SELECT Syntax

The core statement used to retrieve data from one or more tables.

SELECT [DISTINCT] column1, column2, ...
FROM table1
WHERE condition
GROUP BY column1
HAVING group_condition
ORDER BY column1 [ASC|DESC];
ClausePurpose
SELECTChoose which columns/expressions to return
DISTINCTRemove duplicate rows from the result
FROMSpecify source table(s) or query(ies)
WHEREFilter rows before grouping
GROUP BYCollapse rows into summary groups
HAVINGFilter groups after aggregation
ORDER BYSort the final result set

Column aliases & identifiers

SELECT FirstName & " " & LastName AS FullName
FROM Employees;

-- Names with spaces or reserved words need square brackets:
SELECT [Order Date], [Customer ID]
FROM [Order Details];
Access uses square brackets [ ] for identifiers with spaces or special characters - not double quotes or backticks like MySQL/Postgres.

Tips & hacks:
  • Run SELECT TOP 1 * FROM TableName; first when exploring an unfamiliar table - it's the fastest way to see all its columns and a sample row.
  • Aliases created with AS automatically become the field captions in bound forms and reports, so pick names your users will actually see.
  • You don't need to select columns in the same order as the table definition - the SELECT list controls output order, not the table.
  • Switch between Design View and SQL View (View menu) to hand-edit complex expressions faster than building them in the grid.

3. Sorting, TOP & DISTINCT

SELECT TOP 10 ProductName, UnitPrice
FROM Products
ORDER BY UnitPrice DESC;

-- Percent version
SELECT TOP 25 PERCENT * FROM Orders ORDER BY OrderDate DESC;

-- Unique combinations only
SELECT DISTINCT City, Country FROM Customers;
Access has no LIMIT ... OFFSET or FETCH FIRST - TOP n (optionally with PERCENT) is the equivalent, and it must be paired with ORDER BY to be meaningful.

Five Examples - Different Cases

  1. Single-column sort, ascending (default): 
    SELECT CompanyName FROM Customers ORDER BY CompanyName;
  2. Multi-column sort with mixed direction: 
    SELECT Country, CompanyName FROM Customers
ORDER BY Country ASC, CompanyName DESC;
  3. Highest N rows (TOP): 
    SELECT TOP 5 ProductName, UnitPrice
FROM Products ORDER BY UnitPrice DESC;
  4. Lowest N rows (reverse the ORDER BY direction): 
    SELECT TOP 5 ProductName, UnitPrice
FROM Products ORDER BY UnitPrice ASC;
  5. Unique rows only, sorted: 
    SELECT DISTINCT Country FROM Customers ORDER BY Country;
Tips & hacks:
  • Access has no TOP n WITH TIES - if several rows tie for the last spot, only n rows come back and the tie-break is arbitrary. Add a secondary ORDER BY column to make it deterministic.
  • To get the "bottom N" instead of top N, keep TOP n but flip ORDER BY from DESC to ASC.
  • Sorting by column position (ORDER BY 2 DESC) works in Access but breaks silently if columns are reordered - prefer naming the column.
  • SELECT DISTINCT combined with TOP is a quick way to get "top N unique values" without a GROUP BY.
  • TOP 1 with an ORDER BY is a handy substitute for "get the most recent record" when there's no aggregate involved.

4. Joins

Access requires parentheses around joined tables when combined with additional joins.

Join typeDescription
INNER JOINOnly matching rows in both tables
LEFT JOINAll rows from left table, matched rows from right (NULLs if none)
RIGHT JOINAll rows from right table, matched rows from left
SELECT o.OrderID, c.CompanyName
FROM Orders AS o
INNER JOIN Customers AS c ON o.CustomerID = c.CustomerID;

SELECT c.CompanyName, o.OrderID
FROM Customers AS c
LEFT JOIN Orders AS o ON c.CustomerID = o.CustomerID;

-- Multiple joins need nested parentheses in Access
SELECT o.OrderID, c.CompanyName, e.LastName
FROM (Orders AS o
INNER JOIN Customers AS c ON o.CustomerID = c.CustomerID)
INNER JOIN Employees AS e ON o.EmployeeID = e.EmployeeID;
Access has no FULL OUTER JOIN. Simulate it with a UNION of a LEFT JOIN and a RIGHT JOIN (see Union section).

Five Examples - Different Cases

  1. Basic INNER JOIN: 
    SELECT o.OrderID, c.CompanyName
FROM Orders AS o
INNER JOIN Customers AS c ON o.CustomerID = c.CustomerID;
  2. LEFT JOIN to include unmatched rows: 
    SELECT c.CompanyName, o.OrderID
FROM Customers AS c
LEFT JOIN Orders AS o ON c.CustomerID = o.CustomerID;
  3. Anti-join - find rows with NO match: 
    SELECT c.CompanyName
FROM Customers AS c
LEFT JOIN Orders AS o ON c.CustomerID = o.CustomerID
WHERE o.OrderID IS NULL;
  4. Self-join - employees and their managers: 
    SELECT e.LastName AS Employee, m.LastName AS Manager
FROM Employees AS e
INNER JOIN Employees AS m ON e.ReportsTo = m.EmployeeID;
  5. Three-table join (note the nested parentheses): 
    SELECT o.OrderID, c.CompanyName, e.LastName
FROM (Orders AS o
INNER JOIN Customers AS c ON o.CustomerID = c.CustomerID)
INNER JOIN Employees AS e ON o.EmployeeID = e.EmployeeID;
Tips & hacks:
  • Always alias every table (AS o, AS c) in a join - it keeps column references short and avoids ambiguity errors on shared column names.
  • The "LEFT JOIN + WHERE right.key IS NULL" pattern is the standard Access way to find orphaned or unmatched records (customers with no orders, products never sold, etc.).
  • Three or more tables always need nested parentheses in Access's FROM clause - the query grid adds these automatically, but hand-written SQL must include them.
  • A self-join (joining a table to itself with two aliases) is the go-to technique for hierarchical data like employee/manager or category/parent-category relationships.
  • If a query design view join won't let you pick LEFT vs RIGHT, just switch to SQL View and edit the JOIN keyword directly - it's fully editable there.

4a. Non-Equi Joins

An ordinary (equi) join matches rows when two columns are equal - usually a primary key to a foreign key. A non-equi join matches rows using any other comparison: <, >, <=, >=, <>, or a range with BETWEEN.

What and why

Equi joinNon-equi join
Conditiona.CustomerID = b.CustomerIDa.Amount >= b.MinAmount
RelationshipKey to keyValue to range, or row to "earlier/later/other" rows
Matches per rowUsually one (or a few)Often many - rows can multiply
Typical useAttach related dataBands, tiers, pairs, running totals, overlaps

Think of a join as: pair every row of A with every row of B, then keep only the pairs where the ON condition is true. With = few pairs survive; with < or a range, many do. That is the whole idea - the examples below just show it three ways.

1. Range lookup (basic)

Scenario: Label every order Small, Medium or Large. The labels live in a tier table - there is no shared key, only a range that each amount falls into.

TierNameMinAmountMaxAmount

SELECT o.OrderID, o.OrderAmount, t.TierName
FROM Orders AS o
INNER JOIN Tiers AS t
  ON o.OrderAmount >= t.MinAmount
 AND o.OrderAmount <= t.MaxAmount;

Logic: each order is tested against every tier; exactly one range contains it, so exactly one row survives. Order 103 (120.00) fails Medium and Large, passes Small.

2. Self join: unique pairs

Scenario: List every pair of products in the same category so prices can be compared. A self join uses the same table twice under two aliases (a and b).

SELECT a.ProductName AS ProductA, b.ProductName AS ProductB,
       a.UnitPrice AS PriceA, b.UnitPrice AS PriceB
FROM Products AS a
INNER JOIN Products AS b
  ON a.CategoryID = b.CategoryID
 AND a.ProductID < b.ProductID;

Logic: the equality alone pairs Widget A with itself, with Widget B, and Widget B with Widget A again. Category 1 would give four rows:

3. Self join: running total

Scenario: Show each order with the total sales up to and including that order, in date order. For every order, we need to gather all orders on or before its date - a "one row to many rows" match that only a non-equi join can do.

SELECT cur.OrderID, cur.OrderDate, cur.OrderAmount,
       SUM(prev.OrderAmount) AS RunningTotal
FROM Orders AS cur
INNER JOIN Orders AS prev
  ON prev.OrderDate <= cur.OrderDate
GROUP BY cur.OrderID, cur.OrderDate, cur.OrderAmount
ORDER BY cur.OrderDate;

Logic, for order 103 (2026-02-20): cur is fixed on 103; prev keeps every order dated on or before 2026-02-20, which is 101, 102 and 103. GROUP BY collapses those matches and SUM adds them: 250 + 780 + 120 = 1150.

  • Write non-equi joins in SQL View; Access Design View often cannot display them.
  • Use <= to include the row itself (running total); use < to exclude it (unique pairs).
  • Rows multiply, so check the row count. Aggregate with GROUP BY when you want one row per original record.
  • If two orders share a date, <= on date counts both for each. Use OrderID as a tie-breaker when exact order matters.

4b. Single-Row (Scalar) Functions

Single-row functions operate on one row at a time and return exactly one value per row - as opposed to aggregate functions (next section), which collapse many rows into one summary value per group. Five More Examples - Different Cases

  1. Extract initials from two fields: 
    SELECT Left(FirstName,1) & Left(LastName,1) AS Initials
FROM Employees;
  2. Find and flag records missing an "@" in an email field: 
    SELECT Email, InStr(Email,"@") AS AtPosition
FROM Customers
WHERE InStr(Email,"@") = 0;
  3. Clean up inconsistent spacing and casing: 
    SELECT Trim(UCase(CompanyName)) AS CleanName
FROM Customers;
  4. Round a price down/up differently depending on sign: 
    SELECT UnitPrice, Int(UnitPrice) AS FloorPrice, Fix(UnitPrice) AS TruncPrice
FROM Products;
  5. Mask part of a value (e.g. a reference code) for display: 
    SELECT OrderID, "ORD-" & Right("0000" & OrderID, 4) AS OrderRef
FROM Orders;
Tips & hacks:
  • Right("0000" & Number, 4) is a classic zero-padding hack when Access has no built-in PAD() function - pad first, then take the rightmost N characters.
  • Int() and Fix() only differ on negative numbers - for positive prices and quantities they behave identically; reach for Fix() if you specifically need "toward zero" truncation.
  • Nest Trim() around UCase()/LCase() to normalize messy imported text data (extra spaces plus inconsistent case) in a single expression.
  • InStr() returning 0 means "not found" - test for that explicitly rather than assuming a positive number always comes back.
  • Single-row functions can be nested arbitrarily deep (as in the Initials example), but for readability, pull very long nested expressions into a saved query or a VBA function instead.

Five Examples - Different Cases

  1. Simple count and sum: 
    SELECT COUNT(*) AS TotalOrders, SUM(OrderAmount) AS Revenue
FROM Orders;
  2. Group by one column with multiple aggregates: 
    SELECT CustomerID, COUNT(*) AS OrderCount, SUM(OrderAmount) AS Total
FROM Orders
GROUP BY CustomerID;
  3. Group by two columns: 
    SELECT CategoryID, Discontinued, AVG(UnitPrice) AS AvgPrice
FROM Products
GROUP BY CategoryID, Discontinued;
  4. Conditional ("distinct-style") count using IIf inside SUM: 
    SELECT CustomerID,
       SUM(IIf(OrderAmount > 500, 1, 0)) AS BigOrders
FROM Orders
GROUP BY CustomerID;
  5. Filter groups with HAVING on a calculated total: 
    SELECT CustomerID, SUM(OrderAmount) AS Total
FROM Orders
GROUP BY CustomerID
HAVING SUM(OrderAmount) > 1000;
Tips & hacks:
  • Access has no COUNT(DISTINCT col) - the standard workaround is SELECT COUNT(*) FROM (SELECT DISTINCT col FROM Table), or a GROUP BY subquery.
  • Remember WHERE filters rows before grouping and HAVING filters groups after - put row-level conditions in WHERE for better performance, and only use HAVING for conditions on the aggregate itself.
  • SUM(IIf(condition, 1, 0)) is the standard Access "conditional count" pattern, since there's no COUNT(CASE WHEN...) syntax.
  • Every non-aggregated column in the SELECT list must appear in GROUP BY, or Access will raise an error - unlike some engines that silently pick an arbitrary value.
  • First()/Last() depend on the underlying storage/retrieval order, which isn't guaranteed - don't rely on them for anything order-sensitive without an explicit subquery ordering first.

6. Subqueries

-- In WHERE
SELECT ProductName FROM Products
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM Products);

-- With IN
SELECT CustomerID FROM Customers
WHERE CustomerID IN (SELECT CustomerID FROM Orders WHERE OrderDate > #1/1/2026#);

-- EXISTS
SELECT CompanyName FROM Customers AS c
WHERE EXISTS (SELECT 1 FROM Orders AS o WHERE o.CustomerID = c.CustomerID);

-- As a derived table
SELECT Country, AvgPrice
FROM (SELECT Country, AVG(UnitPrice) AS AvgPrice FROM Products GROUP BY Country) AS T
WHERE AvgPrice > 20;

Five Examples - Different Cases

  1. Scalar subquery in WHERE: 
    SELECT ProductName FROM Products
WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM Products);
  2. Subquery in the SELECT list: 
    SELECT CompanyName,
       (SELECT COUNT(*) FROM Orders WHERE Orders.CustomerID = Customers.CustomerID) AS OrderCount
FROM Customers;
  3. NOT IN - customers who have never ordered: 
    SELECT CompanyName FROM Customers
WHERE CustomerID NOT IN (SELECT CustomerID FROM Orders);
  4. Correlated EXISTS: 
    SELECT CompanyName FROM Customers AS c
WHERE EXISTS (SELECT 1 FROM Orders AS o WHERE o.CustomerID = c.CustomerID);
  5. Subquery as a derived table (FROM clause): 
    SELECT Country, AvgPrice
FROM (SELECT Country, AVG(UnitPrice) AS AvgPrice FROM Products GROUP BY Country) AS T
WHERE AvgPrice > 20;
Tips & hacks:
  • Careful with NOT IN and Nulls: if the subquery's column can ever return a Null, NOT IN silently returns zero rows for the whole query. Add WHERE col IS NOT NULL inside the subquery, or use NOT EXISTS instead - it doesn't have this trap.
  • EXISTS/NOT EXISTS often perform better than IN/NOT IN on larger tables because Access can stop scanning as soon as one match is found.
  • A correlated subquery in the SELECT list (Example 2) runs once per outer row - fine for small tables, but for large ones a LEFT JOIN + GROUP BY is usually faster.
  • Derived tables (subqueries in FROM) must always have an alias in Access - FROM (...) AS T - leaving it off raises a syntax error.
  • Save a frequently reused subquery as its own named query object, then reference that query by name in FROM - it's easier to maintain than repeating the same subquery everywhere.

13. Database Normalization Techniques

Normalization is the process of organizing tables so each fact is stored once, in the right place - it removes redundancy, prevents update/insert/delete anomalies, and is what turns a messy spreadsheet-style table into a proper relational database ready for Access SQL.

Normal FormRuleWhat it fixes
1NF
First Normal Form		Every column holds a single, atomic value. No repeating groups or comma-separated lists in one field.Multi-valued / repeating columns
2NF
Second Normal Form		Must already be in 1NF, and every non-key column depends on the whole primary key (only relevant when the key is composite, e.g. OrderID + ProductID).Partial dependencies
3NF
Third Normal Form		Must already be in 2NF, and no non-key column depends on another non-key column instead of the key.Transitive dependencies
BCNF
Boyce–Codd (optional)		A stricter version of 3NF: every determinant (any column that determines another) must itself be a candidate key.Rare edge cases 3NF misses
Most real-world Access databases only need to reach 3NF. Going further (BCNF and beyond) is usually academic unless you have unusual overlapping candidate keys.

Step-by-Step Worked Example: Unnormalized → 1NF → 2NF → 3NF

Starting point - a single flat "OrderData" table exactly as it might arrive from an Excel export. It mixes order info, customer info, and a repeating list of products into one row per order.

Step 1 - Apply 1NF: split the repeating "Products" list so each product on an order gets its own row. The primary key becomes composite: (OrderID, ProductID).

OrderID | OrderDate  | CustomerName | CustomerPhone | ProductName  | Qty | Price
1001    | 05/01/2026 | Jane Doe     | 555-1234       | Choco Bar    | 3   | 2.00
1001    | 05/01/2026 | Jane Doe     | 555-1234       | Choco Bites  | 1   | 5.00
1002    | 06/01/2026 | Willy Wonka  | 555-9876       | Almond Bar   | 2   | 3.50

Atomic values now - no more comma-separated lists. But CustomerName, CustomerPhone, OrderDate repeat on every product line, and ProductName/Price only really depend on the product, not on the order.

Step 2 - Apply 2NF: the primary key is (OrderID, ProductID), but ProductName and Price depend only on ProductID - a partial dependency on part of the key. Pull those into their own Products table.

-- Orders (one row per order - OrderDate/Customer still repeated per line item, fixed in 3NF)
OrderID | OrderDate  | CustomerName | CustomerPhone
1001    | 05/01/2026 | Jane Doe     | 555-1234
1002    | 06/01/2026 | Willy Wonka  | 555-9876

-- OrderDetails (composite key OrderID + ProductID, only order-specific facts remain)
OrderID | ProductID | Qty
1001    | 1         | 3
1001    | 2         | 1
1002    | 3         | 2

-- Products (ProductID is the whole key now, so no partial dependency)
ProductID | ProductName  | Price
1         | Choco Bar    | 2.00
2         | Choco Bites  | 5.00
3         | Almond Bar   | 3.50

Step 3 - Apply 3NF: in the Orders table, CustomerPhone depends on CustomerName, not on OrderID - a transitive dependency (OrderID → CustomerName → CustomerPhone). Split customers into their own table.

-- Customers (CustomerPhone now depends only on the key, CustomerID)
CustomerID | CustomerName | CustomerPhone
1          | Jane Doe     | 555-1234
2          | Willy Wonka  | 555-9876

-- Orders (transitive dependency removed - just a foreign key)
OrderID | OrderDate  | CustomerID
1001    | 05/01/2026 | 1
1002    | 06/01/2026 | 2

Final 3NF schema - four tables, each fact stored exactly once, built in Access with:

CREATE TABLE Customers (
    CustomerID    AUTOINCREMENT PRIMARY KEY,
    CustomerName  TEXT(255),
    CustomerPhone TEXT(20)
);

CREATE TABLE Products (
    ProductID   AUTOINCREMENT PRIMARY KEY,
    ProductName TEXT(255),
    Price       CURRENCY
);

CREATE TABLE Orders (
    OrderID    AUTOINCREMENT PRIMARY KEY,
    OrderDate  DATETIME,
    CustomerID LONG,
    CONSTRAINT FK_Orders_Customers FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
);

CREATE TABLE OrderDetails (
    OrderID   LONG,
    ProductID LONG,
    Qty       LONG,

    CONSTRAINT FK_OD_Orders   FOREIGN KEY (OrderID)   REFERENCES Orders(OrderID),
    CONSTRAINT FK_OD_Products FOREIGN KEY (ProductID) REFERENCES Products(ProductID)
);

Five Examples - Different Normalization Scenarios

  1. 1NF - fixing a repeating/multivalued column: a Customers table with a single PhoneNumbers field like "555-1234, 555-9876" violates 1NF. Fix by moving phone numbers to their own table so each number is one atomic row: 
    CREATE TABLE CustomerPhones (
    PhoneID    AUTOINCREMENT PRIMARY KEY,
    CustomerID LONG,
    Phone      TEXT(20),
    PhoneType  TEXT(20)
);
  2. 2NF - removing a partial dependency: an Enrollments table keyed on (StudentID, CourseID) also stores CourseName and Credits, which depend only on CourseID. Move them out: 
    CREATE TABLE Courses (
    CourseID   TEXT(10) PRIMARY KEY,
    CourseName TEXT(255),
    Credits    LONG
);
CREATE TABLE Enrollments (
    StudentID LONG,
    CourseID  TEXT(10),
    Grade     TEXT(2),
    CONSTRAINT PK_Enroll PRIMARY KEY (StudentID, CourseID)
);
  3. 3NF - removing a transitive dependency: an Employees table stores DepartmentID, DepartmentName and DepartmentBudget. The latter two depend on DepartmentID, not on EmployeeID. Split out a Departments table and keep only the foreign key on Employees: 
    CREATE TABLE Departments (
    DepartmentID     AUTOINCREMENT PRIMARY KEY,
    DepartmentName   TEXT(255),
    DepartmentBudget CURRENCY
);
CREATE TABLE Employees (
    EmployeeID   AUTOINCREMENT PRIMARY KEY,
    EmployeeName TEXT(255),
    DepartmentID LONG
);
  4. Many-to-many relationship → junction table: "a student can take many courses, a course can have many students" can't be modeled with a foreign key on either side alone. Add a junction (bridge) table - this is exactly what OrderDetails and Enrollments above already are: 
    CREATE TABLE StudentCourses (
    StudentID LONG,
    CourseID  TEXT(10),
    DateEnrolled DATETIME,
    CONSTRAINT PK_SC PRIMARY KEY (StudentID, CourseID)
);
  5. Deliberate denormalization for reporting: after normalizing, a reporting query that joins four tables every time can be slow. Rather than storing redundant data long-term, build a query (or a saved "reporting" table refreshed on a schedule) that flattens it back out - normalize the base tables, denormalize the view: 
    SELECT o.OrderID, c.CustomerName, p.ProductName, od.Qty, p.Price, (od.Qty * p.Price) AS LineTotal
FROM ((Orders AS o
INNER JOIN Customers AS c ON o.CustomerID = c.CustomerID)
INNER JOIN OrderDetails AS od ON o.OrderID = od.OrderID)
INNER JOIN Products AS p ON od.ProductID = p.ProductID;
Tips & hacks:
  • A quick smell test for 1NF: if you're tempted to store a comma-separated list, a slash-separated pair, or "Product1/Product2" style columns in one field, it needs its own table instead.
  • 2NF only ever matters when the primary key is composite (two or more columns) - a table with a single-column AutoNumber key is automatically in 2NF as long as it's in 1NF.
  • A fast way to spot a transitive dependency (3NF violation): ask "if I delete every order for a customer, do I lose the customer's phone number too?" If yes, that fact belongs in its own table.
  • Always enforce the relationships you've designed in Access's Relationships window with Enforce Referential Integrity switched on - normalization on paper doesn't stop bad data entry without it.
  • Normalize for data entry and integrity, then denormalize (via queries, not by redesigning the tables) for reporting and performance - don't skip straight to a flat table just because the final report needs one.

14. Indexing

An index is a separate, sorted lookup structure Access maintains alongside a table so it can find matching rows without scanning every record - essential once a table grows past a few hundred rows, and directly controllable from SQL View with CREATE INDEX.

-- Basic index (speeds up WHERE / ORDER BY / JOIN on this column)
CREATE INDEX idxCustomerID ON Orders (CustomerID);

-- Unique index (also blocks duplicate values, like a business-rule constraint)
CREATE UNIQUE INDEX idxEmail ON Customers (Email);

-- Composite (multi-column) index
CREATE INDEX idxNameState ON Customers (CustomerName, State);

-- Remove an index
DROP INDEX idxCustomerID ON Orders;
A Primary Key automatically gets a unique index for free - you never need to CREATE INDEX on top of it. CREATE INDEX is for the columns you filter, sort, or join on that aren't already the primary key.

Step-by-Step Worked Example: Indexing the Normalized Schema

Using the Customers / Products / Orders / OrderDetails schema from the Normalization section, here's how to decide what to index and add it.

  1. Identify the columns actually used to filter, sort, or join. In this schema that's: Orders.CustomerID (join target), OrderDetails.ProductID (join target), and Customers.Email (must be unique, looked up on login).
  2. Foreign keys first - Access indexes primary keys automatically, but a foreign key column on the "many" side of a relationship is not indexed automatically unless you enforce referential integrity in the Relationships window. Add it explicitly in SQL View: 
    CREATE INDEX idxOrdersCustomerID ON Orders (CustomerID);
CREATE INDEX idxDetailsProductID ON OrderDetails (ProductID);
  3. Enforce a business rule with a unique index - no two customers should share an email address: 
    CREATE UNIQUE INDEX idxCustomerEmail ON Customers (Email) WITH DISALLOW NULL;
  4. Composite index for a common two-column filter - if reports regularly filter Orders by date range and customer, put the more selective column first: 
    CREATE INDEX idxOrdersCustDate ON Orders (CustomerID, OrderDate);
  5. Verify in the Access UI: open the table in Design View → Indexes button (or ribbon Design → Indexes) to see everything you just created, including which are marked Unique and Primary.

Five Examples - Different Cases

  1. Single-column index to speed up a foreign key lookup: 
    CREATE INDEX idxOrdersCustomerID ON Orders (CustomerID);
    Without this, every query joining Orders to Customers forces Access to scan the entire Orders table for each customer.
  2. Unique index enforcing a business rule, disallowing Nulls: 
    CREATE UNIQUE INDEX idxProductSKU ON Products (SKU) WITH DISALLOW NULL;
    Guarantees every product has a SKU and that no two products share one - an insert violating either fails outright.
  3. Unique index that tolerates Nulls (optional-but-unique field): 
    CREATE UNIQUE INDEX idxSecondaryEmail ON Customers (SecondaryEmail) WITH IGNORE NULL;
    Useful when a field is optional (many customers leave it blank) but must still be unique whenever it is filled in - IGNORE NULL excludes blank entries from the uniqueness check instead of rejecting them.
  4. Composite index matching a real query pattern: 
    CREATE INDEX idxOrdersCustDate ON Orders (CustomerID, OrderDate);

-- This query benefits directly - it filters on the leading column
-- and sorts on the second, both covered by the same index:
SELECT * FROM Orders
WHERE CustomerID = 51
ORDER BY OrderDate DESC;
  5. Dropping an index that's no longer earning its keep: 
    DROP INDEX idxOrdersCustDate ON Orders;
    Do this for indexes on columns that turned out to be rarely queried but are frequently updated - every index adds overhead to every INSERT/UPDATE/DELETE.
Tips & hacks:
  • Column order matters in a composite index - Access can use the leading column(s) alone (a "left-to-right prefix"), but a query filtering only on the second column of (CustomerID, OrderDate) won't benefit from it.
  • Access has a quiet default: any field named exactly ID, or starting/ending with key, code, num, or id (e.g. ProductID) gets auto-indexed when you create it in Table Design view, unless you turn this off under Options → Object Designers → AutoIndex on Import/Create. Fields created purely via SQL DDL don't get this treatment automatically.
  • Don't index every column "just in case" - each extra index makes every write (INSERT/UPDATE/DELETE) slower because Access has to update all of them, and low-selectivity columns (e.g. a Yes/No field) rarely benefit from an index at all.
  • Run Database Tools → Analyze Performance periodically - it will actively suggest missing indexes based on the queries and relationships already in the database.
  • An index on a Memo/Long Text field isn't supported the same way as short text - for searching large text fields, keep a separate short "tag" or "category" column indexed instead of indexing the memo field itself.

Phase 5: Nesting Programming Logic (Interaction Frames)

To model structural logic, surround your messages with rectangular interaction frames.

1. The loop frame (repetition)

Use when the narrative says "for each item", "repeats" or "loops until". Draw a rectangle around the repeating messages, put loop in the top-left tab, and write the guard in square brackets, e.g. [for each product to add].

Reads as: repeat both messages once for every item in the cart. The guard sits in square brackets next to the tab.

2. The alt frame (if-then-else)

Use when there are mutually exclusive outcomes, e.g. "if login is valid... if login is invalid...". Draw one large rectangle around both paths with alt in the top-left tab. Crucial step: split the box in two with a dashed horizontal line. The top half gets the guard [isValid = true], the bottom half [isValid = false].

Reads as: the handler checks the credentials and returns isValid before the frame, so the guards have something to test. If valid go to the main menu, otherwise go to the failure screen. The dashed divider separates the two halves, and each half has its own guard.

3. The opt frame (optional processing)

Use when the logic goes one way only, e.g. "if the trainer is available, then save the booking". There is no else block. Enclose only the conditional steps, put opt in the top-left tab and add a guard such as [isAvailable = true].

Reads as: only if the trainer is available, create the booking. There is no else half. Note the created Booking box drops down to its own step.

4. The ref frame (invoking another diagram)

Use when the scenario hands off to another complete use case, e.g. "the customer's details are retrieved using another sequence diagram". Draw a clean box spanning the lifelines involved, put ref in the top-left tab and write the name of the referenced use case inside.

Reads as: at this point run the whole Validate Customer diagram, then carry on. Nothing is drawn inside the box except the name; it spans the lifelines it touches.
