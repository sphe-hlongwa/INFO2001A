Bind the controls and load

Binding means a TextBox shows a field of the current record by itself. You never copy values across by hand.

  1. Open the Data Sources window. View → Other Windows → Data Sources. Your table is listed there.
  2. Set the table to Details, using its dropdown, then drag it onto the form. You get a label and a bound TextBox per field.
  3. Check the tray under the form. It now holds the BindingSource and TableAdapter. Rename the TextBoxes if you like (txtName).
Or by handSelect a TextBox → Properties → (DataBindings) → Text → pick the BindingSource and a field.

Form Load: fill the DataSet

Visual Studio normally writes this for you when you drag from Data Sources.

private void CustomerForm_Load(object sender, EventArgs e)
{
    this.customersTableAdapter.Fill(
        this.crudDemoDataSet.Customers);
}

After Fill() the BindingSource holds the rows and the TextBoxes show the current one.

CarefulThe Designer already writes the bindings (in InitializeComponent). Do not add them again in code, and do not open your own OleDbConnection. The typed DataSet already has one.

Save and Update EndEdit() + Update()

Saving a new row and updating an edited one use the same code. The user types in the TextBoxes, then:

private void btnSave_Click(object sender, EventArgs e)
{
    try
    {
        this.Validate();
        this.customersBindingSource.EndEdit();
        this.customersTableAdapter.Update(
            this.crudDemoDataSet.Customers);

        MessageBox.Show("Record saved.");
    }
    catch (Exception ex)
    {
        MessageBox.Show(
            "The record could not be saved.\n" + ex.Message);
    }
}
Validate()→EndEdit()→Update()

EndEdit pushes the TextBox values into the row. Update writes the row to Access. The MessageBox is your user feedback.

Related tablesIf Visual Studio made a TableAdapterManager, use tableAdapterManager.UpdateAll(dataSet) to save several tables together.
Delete RemoveCurrent() + Update()

Ask first, then remove the current row and send it to Access.

private void btnDelete_Click(object sender, EventArgs e)
{
    if (customersBindingSource.Current == null)
        return;

    DialogResult result = MessageBox.Show(
        "Are you sure you want to delete this record?",
        "Confirm Delete",
        MessageBoxButtons.YesNo,
        MessageBoxIcon.Warning);

    if (result != DialogResult.Yes)
        return;

    try
    {
        customersBindingSource.RemoveCurrent();
        this.Validate();
        customersBindingSource.EndEdit();
        customersTableAdapter.Update(
            crudDemoDataSet.Customers);

        MessageBox.Show("Record deleted.");
    }
    catch (Exception ex)
    {
        MessageBox.Show(
            "The record could not be deleted.\n" + ex.Message);
    }
}

The objects between your form and Access

ADO.NET is a small set of objects. Each does one job. If you can say which object owns an action, you understand the code.

A SELECT travels: button click → Connection opens → Command carries the SQL → Provider translates → Access answers → rows return through a Reader or Adapter → DataTable → BindingSource → the controls.

The connection string

Settings that tell the provider how to reach the source.

Provider=Microsoft.ACE.OLEDB.12.0;Data Source=C:\path\EduGrant.accdb;
Provider

Names the Access engine. The exact one depends on what is installed.

Data Source

Points at the .accdb file. Keep the path configurable between machines.

Why keep the layers apart?

Form

Collects input and explains errors.

Application logic

Rules that can be reused outside a button click.

Data access

Knows the SQL and provider details.

Read path: a JOIN to display

SELECT a.ApplicationID, s.StudentName,
       f.TypeName, a.RequestedAmount, a.Status
FROM (FundingApplication AS a
INNER JOIN Student AS s ON a.StudentID = s.StudentID)
INNER JOIN FundingType AS f
  ON a.FundingTypeID = f.FundingTypeID

Access commonly needs parentheses around multiple joins. The screen shows names; the stored table still holds only IDs.

Write path: save the ID, show the name

cmbType.DataSource = fundingTypes;          // a populated DataTable
cmbType.DisplayMember = "TypeName";         // what the student sees
cmbType.ValueMember = "FundingTypeID";      // what the application receives

// On submit, after checking something is selected:
int typeId = Convert.ToInt32(cmbType.SelectedValue);
// INSERT FundingTypeID = typeId, not the TypeName
TipSet DropDownStyle to DropDownList if free typing is not allowed, then check a real item is chosen.

Ask these before building any combined screen

Which table owns each displayed value? Which key connects the rows? Which value do I save? What if the related record is missing or inactive? Show the current label or a historical snapshot?

Amount example

if (!decimal.TryParse(txtAmount.Text, out var amount) || amount <= 0m)
{
    errorProvider.SetError(txtAmount,
        "Enter an amount greater than R0.");
    return;
}
Why TryParseBad text becomes a predictable false, not a FormatException. Predictable invalid input belongs in validation, not in exception handling.

Timing and wording

Avoid

“Invalid input”. The user is left guessing, and the form may wipe what they typed.

Better

Name the field and the fix, keep the values, focus the first invalid control, and check the whole operation on Submit.

CRUD and moving through records

Every operation needs an identified target and a visible outcome. Open each one.

Create INSERT
Validate→INSERT with parameters→Check rows affected→Refresh and confirm
var sql = "INSERT INTO FundingApplication " +
    "(StudentID, RequestedAmount, Status) VALUES (?, ?, ?)";
using var cmd = new OleDbCommand(sql, connection);
cmd.Parameters.AddWithValue("?", studentId);
cmd.Parameters.AddWithValue("?", amount);
cmd.Parameters.AddWithValue("?", "Pending");
int rows = cmd.ExecuteNonQuery();

The database assigns the AutoNumber ID. Add values in the same order as the ? marks. AddWithValue is short for teaching; use explicit OleDbType when you know the field types.

Read SELECT

Rows come back through a reader or DataAdapter.Fill. A COUNT(*) is one value, so use ExecuteScalar. Request only the columns the screen needs.

var table = new DataTable();
using var adapter = new OleDbDataAdapter(
    "SELECT ApplicationID, Status, SubmittedAt FROM FundingApplication", connection);
adapter.Fill(table);
bindingSource.DataSource = table;
dataGridView.DataSource = bindingSource;
Update UPDATE 
UPDATE FundingApplication
SET RequestedAmount = ?, Motivation = ?
WHERE ApplicationID = ?

Target the row by its primary key. Parameters go in order: amount, motivation, then ID. Validate first, check rows affected (0 means no such record), then refresh. A selected display position is not a stable key.

Delete DELETE 
DELETE FROM FundingApplication WHERE ApplicationID = ?

A business decision. Confirm the target and explain the consequence, check whether related records or audit rules prevent it, and consider a Cancelled status to preserve history. Never delete by grid row number.

Navigation

BindingSource.Position tracks the in-memory current item. First, previous, next and last act on the loaded results and issue no SQL.

bindingSource.MovePrevious();
labelPosition.Text =
    $"{bindingSource.Position + 1} of {bindingSource.Count}";
Do
  • Show “3 of 18”
  • Disable impossible moves
  • Handle an empty list first
Remember
  • Sorting or filtering changes the index
  • After a refresh, reselect by ID
  • Never UPDATE or DELETE by position

Search and filter

Define what the user is trying to find, then pick the retrieval method before writing UI code.

SearchLocate a known record or text.
FilterNarrow a list by status or type.
SortChange order, not membership.
NavigateMove among current results.
Exact key or partial text = vs LIKE

Known ID: WHERE ApplicationID = ?. A missing result is a normal no-match, not necessarily an exception.

PatternMatches
Moko%names beginning with Moko
%Moko%names containing Moko
M_koone unknown character
var sql = "SELECT StudentID, StudentName FROM Student " +
          "WHERE StudentName LIKE ? ORDER BY StudentName";
using var cmd = new OleDbCommand(sql, connection);
cmd.Parameters.Add("@pattern", OleDbType.VarWChar)
   .Value = "%" + term.Trim() + "%";
using var reader = cmd.ExecuteReader();

The whole pattern, wildcards included, is the parameter value. The user's text stays a value.

Wildcard families careful
ANSI-89

Access query design: * for many, ? for one.

ANSI-92

OLE DB query: % for many, _ for one.

CarefulDo not mix families in one query. The database setting and query route decide which applies, so test a known prefix and a no-match on the lab machine. The ? placeholder and the ? wildcard are different things.
Database WHERE or local filter? where to cut
Database WHERE

Fetches fewer records from Access. Use when data can change or the loaded set is incomplete.

Local filter

Narrows rows already loaded. Fine for a small, permitted set.

A local filter cannot find rows that were never loaded, and it is not an access-control measure.

Status, type and dates exact filters 
SELECT ApplicationID, StudentID, Status
FROM FundingApplication
WHERE Status = ? AND FundingTypeID = ?
ORDER BY SubmittedAt DESC

Add parameters in the same order: status first, type second. For a date range, compare Date/Time fields with typed DateTime parameters, never formatted strings, and decide whether the end date is included.

Make search friendly state is visible
  • Show count and criteria: “12 pending”
  • Explain zero results, offer Clear filters
  • Do not auto-select the first record
  • Keep the current selection stable
  • Show an ID to tell same names apart
  • Limit very large unrestricted searches

Drill: choose the retrieval

Usable, readable, accessible

Appearance should make the task easier to understand. The user should always recognise the next step.

Task and language
  • Order fields as the student thinks
  • Say “Funding type”, not FundingTypeID
  • Group related fields, mark required ones
  • Plain-language status and outcome
Feedback and prevention
  • Show progress on slow operations
  • Block duplicate submits while saving
  • Confirm success with a useful ID
  • Keep input after a failure, offer Cancel
Accessibility
  • Complete a task by keyboard, in a logical TabIndex
  • Clear labels and accessible names
  • Errors need text or an icon, not colour alone
  • Contrast, text size and Windows scaling
Consistency
  • Same words for the same concept
  • Equivalent actions in predictable places
  • Same control for the same kind of choice
  • Similar validation and status messages

Evaluate with evidence, not opinion

  1. Ask someone to finish the form by keyboard only.
  2. Watch whether they find and fix a validation error.
  3. Compare labels, actions and messages across two screens.
  4. Test realistic data, window sizes and display scaling.
  5. Record the problem, its consequence and the correction.
NoteA design heuristic is not a measured outcome. Consistency means keeping useful conventions, not forcing every screen into one layout.

When things go wrong

An exception means an operation cannot continue normally. Catch it only where you can recover, explain or record it.

Validation

A predictable bad value, such as text in an amount box. decimal.TryParse returns false.

Exception

An operational failure, such as the database cannot be opened. decimal.Parse would throw FormatException.

Which exception, where

TypeMeans
OleDbExceptionProvider, query or database failure
InvalidOperationExceptionInvalid object state or misuse
FormatExceptionParsing by a throwing API
IOException, UnauthorizedAccessExceptionFile access, in applicable code paths
ExceptionAn unanticipated defect or condition

The exact type depends on where the failure happens. Access file failures often surface as OleDbException.

try, catch, finally, using

btnSubmit.Enabled = false;
try
{
    SaveValidatedApplication();
    ShowSuccess();                 // only after confirmed success
}
catch (OleDbException ex)
{
    Log(ex);                       // technical detail kept separately
    ShowSaveError();
}
finally
{
    btnSubmit.Enabled = true;      // restore the UI either way
}
catch

Handle a known type. Put specific clauses before broad ones.

finally

Restores UI state whatever happened.

using

Disposes the connection and command even after a failure.

What to tell the user

Never show

SQL text, stack traces or local database paths. “Operation failed” helps nobody.

Do

Say what failed (“The application could not be saved”), offer a next step, and keep their input.
